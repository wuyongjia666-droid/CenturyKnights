## 2. 两种选择

### 选项 A：放宽到 Path C 精致款现状

把 §7.3 的 CI 代理指标和 §7.4 的包体条改成下面这样，并写进 `pathc_ship_gate`（只看 git 跟踪文件，顺带修审阅 P2-2）：

- 每件航运档 ≤ 15k 三角（现状最大 14,477，留约 3.6% 余量；不是从性能推导出来的数）
- 每件 ≤ 1 张贴图，边长 ≤ 512，JPG 或 WebP
- 每人 draw call ≤ 2（身体 + 武器）。现有 12 件还没有实测值，要先测，测出来超标就要合并网格
- 包体：棋子资源总量设预算，而不是只算「增量 ≤ 3MB」。现状 8.6MB。**铺满 32 职的估算**（现在只有 3 职有外套，铺满是指 32 职都做外套）：外套按每职男女两件、每件约 0.52MB（现有 6 件外套的平均值），共 64 件约 33MB；武器至少还缺 staff、banner、club 3 件，留余量按 5 件、每件约 0.44MB 算。合计约 **38–42MB**。现有的 8.6MB 已经算在 #316 的 567.4MB APK 里，所以铺满后 APK 大约再增加 30MB，需要对应调高 `ratchet.json` 的 `export_base_budget_bytes`，或者走职业共壳来减少件数
- 性能门槛（中端安卓 16 单位 ≥ 58fps 等）不变。按 16 人 × 15k 算是 24 万三角。§3.7 估算的「现状约 65 万」是旧棋子 16 人加描边 pass 的总量，口径相同，但还要实机验证

代价是包体上涨，而且手机端的面数比原设计高一倍多。好处是和用户已经认可的画面一致，不用返工。

### 选项 B：守住原门槛

- §7.3 / §7.4 不改
- 航运档要降到 ≤ 7k 三角：发型和外套做棋盘 LOD，按 §3.7 的分配表
- 贴图回到 0 张（顶点色加调色槽）。或者只为脸保留运行时生成的贴花：#310 的 P1b/P1c 已经是运行时投影，不新增贴图文件
- 把 §7.3 的 CI 代理指标真正写进 `pathc_ship_gate`，现有 12 件会立刻红，要逐件返工
- 包体守住增量 ≤ 3MB，铺满 32 职也不会大幅上涨

代价是要重做现有 12 件和 4 件武器的 LOD。用户三次否决的正是「纯色槽」画面（脸不像、糊和锯齿、配色不对），而「顶点色加调色槽」本质上就是纯色槽，所以高概率会再次被否决；能否靠运行时脸贴花补回来，要先做 3 个单位过审再定。好处是包体和手机性能有余量。
