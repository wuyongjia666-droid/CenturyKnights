# 棋子 §7 门槛提案：放宽到 Path C 现状 vs 守住原门槛（2026-10-17）

> 只是提案，不改任何资源、代码和门禁。等用户拍板后，再另开 PR 改 `pawn-redesign-opus.md` §7.3/§7.4 和 `tools/ci/pathc_ship_gate.py`。
> 来源：2026-10-17 全量审阅 P1-5（`.multiagent/runs/review-20261017/REPORT.md`）。

## 1. 现状与原门槛的差距

| 项 | §7.3 / §7.4 原门槛 | Path C 航运档现状（main@c169962d） |
|---|---|---|
| 每人三角 | ≤ 7k（参考 4k–6k） | 11,976–14,477（12 件 `assets/models/board/pathc_ship/*.glb`） |
| 贴图 | 0 张 | 每件 1 张 512×512 JPG albedo（嵌在 GLB 里，另有同名 .jpg） |
| 包体增量 | ≤ 3MB | `pathc_ship` 6,885,078 B + `pathc_weapons` 1,745,998 B ≈ **8.6MB** |
| draw call | 每人 1 个 | 未测 |
| CI 门禁 | 写在 §7.3 的「CI 代理指标」 | `pathc_ship_gate` 只卡单文件 > 5MB、> 100k 三角，§7.3 实际没有门禁 |
| 覆盖 | 32 职 | 有外套的只有 3 职（hunter、leader_coat、light_inf，各分男女）；武器 4 件（剑、矛、斧、弓），staff（11 职）、banner（3 职）、club（`bandit_weak`）都没有 |

#310 的偏离记录（`pawn-redesign-opus.md` 附录「#310 P1 偏离记录」）已经写明：0 贴图规则是在用户三次否决纯色槽之后放弃的。所以「0 贴图」这一条和已拍板的画面方向冲突。

## 2. 两种选择

### 选项 A：放宽到 Path C 精致款现状

把 §7.3 的 CI 代理指标和 §7.4 的包体条改成下面这样，并写进 `pathc_ship_gate`（只看 git 跟踪文件，顺带修审阅 P2-2）：

- 每件航运档 ≤ 15k 三角（现状最大 14,477）
- 每件 ≤ 1 张贴图，边长 ≤ 512，JPG 或 WebP
- 每人 draw call ≤ 2（身体 + 武器），需要补测
- 包体：棋子资源总量设预算，而不是只算「增量 ≤ 3MB」。现状 8.6MB。**铺满 32 职的估算**：外套按每职男女两件、每件约 0.52MB，共约 33MB；再补 staff、banner、club 等约 5 件武器，每件约 0.44MB。合计约 **38–42MB**，需要对应调高 `ratchet.json` 的 `export_base_budget_bytes`，或者走职业共壳来减少件数
- 性能门槛（中端安卓 16 单位 ≥ 58fps 等）不变。按 16 人 × 15k 算是 24 万三角，在 §3.7 估算的「现状约 65 万」以下，但还要实机验证

代价是包体上涨，而且手机端的面数比原设计高一倍多。好处是和用户已经认可的画面一致，不用返工。

### 选项 B：守住原门槛

- §7.3 / §7.4 不改
- 航运档要降到 ≤ 7k 三角：发型和外套做棋盘 LOD，按 §3.7 的分配表
- 贴图回到 0 张（顶点色加调色槽）。或者只为脸保留运行时生成的贴花：#310 的 P1b/P1c 已经是运行时投影，不新增贴图文件
- 把 §7.3 的 CI 代理指标真正写进 `pathc_ship_gate`，现有 12 件会立刻红，要逐件返工
- 包体守住增量 ≤ 3MB，铺满 32 职也不会大幅上涨

代价是要重做现有 12 件和 4 件武器的 LOD。0 贴图的画面曾三次被用户否决，返工后可能再次达不到「像立绘里的那个人」。好处是包体和手机性能有余量。

## 3. 建议的折中（供参考，不替用户决定）

- 桌面和中高端安卓用 A 的规格。
- 低端机走 §3.8 已有的「烘焙替身」档：开局把棋子渲染成 2D 精灵，面数和贴图不进运行时预算。
- 包体按「铺满 32 职」的实际估算设预算，并和 Android 瘦包（#316，APK 795.6MB → 567.4MB）一起核对。
